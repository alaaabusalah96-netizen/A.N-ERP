# قرار معماري: سياسة ملفات تعريف الارتباط وحماية CSRF (ADR 007)
## Architectural Decision Record: Cookie Policy & CSRF Defense-in-Depth — A.N ERP v7.2

**الحالة:** معتمد (Accepted)  
**التاريخ:** 2026-09-20  
**المعيار:** البند 4.6G والبند 8 و 9 من مواصفات النواة  

---

### 1) السياق والمشكلة (Context & Problem)
يعمل نظام A.N ERP كمنصة مؤسسية سحابية لإدارة العمليات المالية والمحاسبية. تُدار جلسات المستخدمين عبر توكنات JWT قصيرة العمر (15 دقيقة) وتوكنات تحديث دورية (Refresh Rotation) مشفرة ومحفوظة حصراً داخل ملفات تعريف ارتباط آمنة (`HttpOnly Secure Cookies`) لحمايتها من هجمات سرقة الجلسات عبر XSS ومنع تخزينها في `localStorage` (وفق البند 8.3).

ومع ذلك، فإن استخدام ملفات تعريف الارتباط للمصادقة قد يعرّض النظام لمحاولات تزوير الطلبات عبر المواقع (Cross-Site Request Forgery - CSRF)، خاصة في بيئات المعاينة المضمنة (Iframe / Cross-Origin Previews) مثل بيئة Google Cloud Run / AI Studio.

---

### 2) القرار الهندسي المعتمد (Decision)
اعتمد النظام استراتيجية حماية متعددة الطبقات (Defense-in-Depth) تدمج بين سياسة الكوكيز الديناميكية والتحقق الصارم من الترويسات ومصدر الطلب دون الحاجة إلى تعقيد تدفقات المستخدم برمز عشوائي ثقيل (Anti-CSRF Token):

#### أ. سياسة ملفات تعريف الارتباط الديناميكية (Dynamic Cookie Policy):
- **الوضع الافتراضي (Top-level Navigation):**
  تُضبط الترويسة بـ `SameSite=Lax; HttpOnly; Secure` في بيئة الإنتاج. هذه السياسة تمنع المتصفحات نهائياً من إرسال كوكيز الجلسة مع أي طلبات POST أو PUT أو DELETE واردة من مواقع خارجية.
- **وضع المعاينة المضمنة (Embedded Iframe Mode):**
  عندما تشير ترويسات المتصفح الوصفية (`sec-fetch-dest: iframe` أو `sec-fetch-site: cross-site`) إلى أن الطلب يمر عبر إطار معاينة شرعي معتمد، تُضبط الكوكيز بـ `SameSite=None; Secure` لتمكين المعاينة التشغيلية.

#### ب. متطلب نوع المحتوى الصارم (`Content-Type: application/json`):
جميع مسارات الأعمال والتعديل المالي تفرض نوع المحتوى `application/json` وترفض أي إرسال عبر نماذج HTML القياسية (`application/x-www-form-urlencoded` أو `multipart/form-data`). المتصفحات تجبر أي طلب خارجي يرسل JSON على تنفيذ فحص مسبق (`CORS Preflight OPTIONS`) لا يمكن تجاوزه.

#### ج. إلزامية ترويسة الإدهنية (`Idempotency-Key`):
وفق البند 8.1 وبند 4.5F، كل عملية تعديل أو ترحيل أو اعتماد تتطلب إرسال الترويسة المخصصة `Idempotency-Key`. وجود ترويسة مخصصة (Custom Header) يمنع هجمات CSRF الكلاسيكية بنسبة 100% لأن النماذج الخارجية والطلبات البسيطة (Simple Requests) عاجزة تماماً عن حقن ترويسات مخصصة دون إذن CORS مسبق.

#### د. وسيط فحص المصدر عبر النطاقات (Origin Verification Middleware):
أضيف وسيط حماية في `server.ts` لجميع عمليات التعديل (`POST`, `PUT`, `PATCH`, `DELETE`):
- إذا تضمن الطلب ترويسة `Origin` أو `Referer` من موقع خارجي غير معتمد، وكان الطلب يفتقر إلى ترويسة مخصصة (`Idempotency-Key` أو `X-Requested-With` أو `Authorization`)، يُرفض الطلب فوراً برمز **403 Forbidden** مع RFC 7807 problem تفصيلي.

---

### 3) العواقب والنتائج (Consequences)
1. **الأمان:** مناعة كاملة ضد هجمات CSRF سواء في التصفح العادي أو عبر النطاقات.
2. **الامتثال:** تحقيق كامل لمتطلبات البند 4.6G دون التأثير على عمل بيئة التطوير والمعاينة.
3. **الأداء:** انعدام أي حمل إضافي على خوادم الذاكرة (Zero Session State Overheads).
